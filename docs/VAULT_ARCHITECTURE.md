# Kgaga Vault — cryptographic architecture

Status: increment 004 development foundation. Local immutable encrypted records, external-file KEK custody, envelope encryption and a separate Vault access policy evaluator. Explicit opt-in HTTPS gateway enforcement, bearer injection and timed credential leases are implemented through increment 007.

## Goal and separation of duties

Identity authenticates an agent; Gateway authorizes its actions; Vault will hold credentials behind the gateway's trust boundary. A passport or holder key must never serve as a vault encryption key. Agents must not be able to select arbitrary secret names, destinations or injection headers. The operator configures those bindings. Future injection must occur after policy checks, only to the authorized verified TLS origin, with no redirect following and no credential-bearing output returned to agents.

## Implemented record primitive (format 1)

- AES-256-GCM via Go's standard library, 32-byte randomly generated data keys, 12-byte cryptographically random nonces and 16-byte authentication tags.
- Generate a new independent data encryption key (DEK) for each immutable record version. Key generation uses crypto/rand. The primitive accepts explicit data keys for decrypting records; it does not enforce their lifecycle or uniqueness.
- Binary encoding: ASCII KGV1 followed by a 12-byte nonce and GCM ciphertext/tag. Plaintext size 1 to 65,536 bytes. No compression or algorithm negotiation.
- Associated authenticated data: ASCII kgaga-vault:record:v1, one zero byte, ASCII KGV1, 16-byte vault identifier, 16-byte data key identifier, 8-byte big-endian positive record version, one-byte name length and exact name bytes. Names contain lowercase ASCII letters, digits, underscore or hyphen (1–64 bytes).
- Caller supplies expected metadata from trusted record context. Substituted vault, name, version or key ID, wrong key and modified ciphertext fail authentication. No plaintext is returned following verification failure.
- This primitive does not protect against replacement with an old valid record and its matching metadata, a compromised host, or a party holding the data key. No secure memory-erasure guarantee in Go.

## Planned storage and key hierarchy

Storage (increment 002): operator-only local Store API, explicit Init(path, vaultID) and Open(path, expectedVaultID), no implicit initialization, private 0700 directory and 0600 regular files. The manifest contains KGS1 and the 16-byte vault ID. Supply the expected identity and data key/key ID independently from trusted caller state. The manifest is not itself a cryptographic trust anchor. Each record path is a validated name, dot, fixed-width 20-digit version, and .kgv suffix; the file contains only the authenticated KGV1 envelope. No plaintext or raw DEK is written. Put encrypts in memory, writes a private temporary file, syncs it, then exclusively publishes with a hard link. Concurrent writers cannot replace the winning version. Get bounds reads and checks file type, permissions, path identity and the expected authenticated record context. An open store pins directory and manifest identity. Normal reopen with the same expected identity and key works; missing, replaced or corrupted state fails closed within the documented trust assumptions.

Only use supported POSIX local filesystems with hard links and protected hierarchy/ownership/ACLs; do not use shared or untrusted writable parents. The file checks are not race-proof against a malicious filesystem writer. File sync precedes publication but directory persistence, power-loss transactions and rollback protection are not established. Failure after publication can be ambiguous; never overwrite an existing version. A crash can leave encrypted .pending files or partial initialization; no automatic cleanup/recovery. Back up encrypted records and independent trusted metadata/key material together using a controlled offline process. No aggregate storage capacity limit or retention policy yet. Use only synthetic data until managed custody, lifecycle and access policies are independently reviewed.

Key hierarchy (increment 003): CreateMasterKey and OpenManaged are trusted internal Store methods. They require explicit expected vault/key identities, an existing private external key parent directory (0700) and a private regular key file (0600), outside the encrypted store. Creation is exclusive; opening never generates missing keys. The external development key file is KGM1 || vault ID (16) || KEK ID (16) || raw AES-256 KEK (32). It is deliberately plaintext in separate operator-protected custody, not a hardware-backed or password-encrypted keystore. Protect its entire hierarchy, backups and permissions; never commit it. File contents are trusted operator state. The loaded KEK is a process snapshot; removing the file does not revoke it. No live rotation or multi-key fallback yet.

ManagedStore.Put generates a fresh DEK and random DEK identity for every attempted encryption. Persist one file in the existing immutable slot: KGE1 || KEK ID (16) || DEK ID (16) || wrap nonce (12) || AES-GCM wrapped DEK and tag (48) || KGV1 encrypted record. The wrapping AAD is ASCII kgaga-vault:wrap:v1, zero byte, KGE1, KEK ID and the complete canonical record AAD. The caller provides the expected name/version; the stored DEK ID is authenticated during unwrap before use. The KEK ID must match the independently configured key. Raw KGV1 and managed KGE1 share the filename namespace and cannot overwrite one another; there is no implicit migration or downgrade fallback. The KEK and raw DEK never appear in KGE1 files. Best-effort clearing of local byte buffers is not guaranteed memory erasure.

Wrapping uses random 96-bit nonces under a shared KEK. Operators must limit each KEK to at most 1,000,000 wrap attempts across all processes, including failed publications, and stop before that ceiling; enforcement and safe rotation are not yet implemented. This is an operational limit, not an enforced quota. Use only synthetic data. No automated deletion, rotation or rollback recovery before lifecycle behavior is implemented. External KMS/HSM custody remains later work.

Access policy (increment 004): separate strict YAML version "1", top-level expected vault_id (32 lowercase hex characters, nonzero), and grants (0–256). Maximum policy file size 128 KiB. Every grant contains exactly agent_id, owner, audience, origin, method, target, mcp_method, tool, required_scopes, secret_name and secret_version. All fields explicit. The immutable policy selection is keyed on exact identity/owner/audience/HTTPS origin/HTTP method/literal target/MCP method/tool. No query, wildcard, prefix fallback, implicit admin override, delegated credentials or agent-selected secret. Require all literal scopes; tools/call additionally requires its exact mcp:tool:<name> scope. REST requires empty MCP fields. Duplicate selectors fail configuration, including selectors with different scopes or secret versions. Return only operator-selected vault ID, secret name and pinned positive version. No header selection in the schema; injection is fixed Authorization bearer credentials only.

Example policy (illustrative; replace with operator-controlled real IDs and origins for synthetic tests):
```yaml
version: "1"
vault_id: "1234567890abcdef1234567890abcdef"
grants:
  - agent_id: "agent-a"
    owner: "owner-a"
    audience: "backend"
    origin: "https://backend.example"
    method: "POST"
    target: "/api/payments"
    mcp_method: ""
    tool: ""
    required_scopes: ["payments:write", "vault:use"]
    secret_name: "service-token"
    secret_version: 2
```

The evaluator requires a trusted context supplied by trusted gateway code after passport verification, holder proof, live registry/trust/revocation/delegation, replay and ordinary gateway authorization. It performs additional identity, holder-binding shape and validity checks, but does not authenticate a claims object by itself; its result is metadata, not a cryptographic capability. Increment 005 uses the selection only inside the gateway. Policy files are trusted operator state and must be protected; changes require reparsing/restart. Empty grants or missing exact match deny Vault access.

Injection (increment 005): explicit opt-in gateway mode requires all five flags --vault-policy, --vault-dir, --vault-id, --vault-kek-file and --vault-kek-id, plus listener TLS and verified upstream HTTPS. The gateway requires redact_secrets: true and checks the entire policy against its exact configured origin, audience and independently expected vault identity at startup. No fallback to ordinary gateway mode after any configuration/authorization/lookup failure. Every protected operation requires ordinary gateway permission plus an exact Vault grant. Public JWKS remains unchanged. The selected immutable managed record is read only after normal admission; live credential and proof freshness checks repeat after lookup. Only Authorization: Bearer is injected, using a bounded 16–4096 byte ASCII RFC 6750 b64token; no client authorization or arbitrary headers forwarded. Stateless MCP tools/call only; session metadata is rejected. Stdio and ordinary non-Vault gateway are unchanged.

The response inspector rejects exact injected token bytes in buffered text/JSON, decoded JSON keys and strings, and released metadata, independently of heuristic scanning. No upstream redirects or uninspected streaming. Errors are generic, without secret values. The trusted upstream necessarily receives the credential and can misuse it, encode/split it or signal it indirectly. This is not comprehensive DLP; backend semantics, trusted TLS PKI, direct-access isolation and operator policy correctness are essential. No guarantee against automatic transport retry, non-atomic revocation/dispatch or memory copies.

Operator-only local CLI: vault-init requires explicit vault-dir, vault-id, vault-kek-file and vault-kek-id; the external key parent must already exist with mode 0700. vault-put uses the same flags plus name, positive version and mandatory --not-before / --expires-at Unix timestamps, reading exact token bytes from protected stdin (no newline, no interactive terminal, no token flag). No read/export command exists. Use only synthetic credentials. Do not place key or credential material in source control, command arguments or logs. A failed vault-init can leave partial state; no automatic overwrite or recovery. The operator must protect both the CLI and master key directory. No global quota, enforced wrap budget or master key rotation yet.

Timed credentials and leases (increment 006): the gateway now requires KGL1 plaintext inside the authenticated KGE1 record: four-byte magic, 8-byte big-endian not-before Unix seconds, 8-byte big-endian expiry Unix seconds, then the bounded bearer bytes. Require positive start, strictly later expiry, at most 3600 seconds validity, and reject already expired provisioning. Reads require start <= current time < expiry. The operator must supply the actual provider validity window or a narrower one; Kgaga cannot certify those times or shorten provider-side validity. Older untimed KGE1 bearer records fail closed in gateway mode; provision a new immutable timed version and update the pinned grant deliberately. No implicit migration, expiry extension or fallback. Raw trusted storage APIs remain unchanged.

Each successful exact grant and timed record retrieval creates an internal, nontransferable single-request lease, capped at 15 seconds or the remaining credential/passport lifetime, whichever is shorter. Consume once after the final live admission and proof check. The upstream context deadline is shortened to the lease deadline, checked before dispatch and after buffering; response release also checks the deadline after live credential validation. No lease registry, public lease ID, renewal or reuse; best-effort buffer clearing only. A new request must pass the entire admission flow again. Time is trusted operator/system state; local monotonic deadlines reduce clock-adjustment effects during an exchange. This bounds gateway-side use, not the actions or lifetime of a token already received by a backend; cancellation is not rollback or proof of exactly-once execution, and transport retry remains possible. Dynamic provider-issued credentials remain future work.

Credential lifecycle (increment 007): vault-put stages a timed immutable version. Explicit vault-activate and vault-revoke use the same vault paths/IDs and name/version flags, without stdin or validity flags. Activation requires a currently valid authenticated timed record at a strictly higher version than any previously activated one. Rotation retires every lower version and never falls back; a policy still grants only its pinned version. Revocation of an active version disables it while retaining the high-water mark. Future revocation denies that version without interrupting the active one, including before provisioning. At most 256 future revocations per name; activation of a higher non-revoked version retires and compacts those below it. Retired/revoked versions cannot be reactivated within maintained state. Existing records need explicit activation; no missing-state auto-admission.

Per-name .lifecycle-<name> files are private 0600, canonical bounded KGC1 metadata: magic, 8-byte high-water mark, one-byte active-version revocation flag, 2-byte count and sorted 8-byte future revocations, followed by HMAC-SHA256. The MAC uses a separate domain-derived key from the operator KEK and binds the payload to the exact vault ID, KEK ID and name. Administrative writers serialize with exclusive per-name directory locks, sync a temporary file, atomically replace the state and sync the parent directory. Busy locks fail without queueing; crash locks require controlled offline inspection. Readers check the latest authenticated state before and after decryption, before lease consumption/dispatch and before releasing an upstream response. Missing state denies all versions; corrupt or unsafe state fails closed and is never silently repaired. Concurrent read/replacement races may deny service rather than return stale data. The raw trusted storage APIs do not enforce gateway lifecycle policy.

Rotate by staging a newer version, intentionally updating the exact pinned policy and explicitly activating the new version. Policy remains startup-bound; old grants stop working as soon as rotation is observed. Coordinating policy restart and activation may cause downtime; no automatic cross-process transaction. Revocation does not erase encrypted records, cancel dispatched actions or revoke provider-side credentials. State HMAC does not prevent restoring an older valid state or operator deletion/reset. Protect state and keys together; never delete lifecycle files or clear crash locks while writers may be active. No general anti-rollback, full crash recovery, master-key rewrapping/rotation, distributed consistency or external provider revocation. Only synthetic credentials.

Later: external secret managers and dynamic issuance, audit, adversarial testing and release review.

## Threat model and operational limits

Trust the operator, operating system and cryptographic randomness. A stolen ciphertext alone should not reveal secret plaintext without its data key. A stolen key can decrypt the matching record. Metadata is authenticated, not necessarily confidential. Ciphertext length reveals approximate secret length. Rollback protection, durable transaction recovery, production key custody, storage capacity management, memory/runtime exposure, complete secret lifecycle, audit and independent gateway assurance are future work. Exclusive publication and mode checks are implemented under protected-filesystem assumptions, not a sandbox. The foundation is not an operational secret manager and must not hold live credentials. Do not publish a production assurance claim based on primitive-level tests.
